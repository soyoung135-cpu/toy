# 이메일·비밀번호 로그인으로 앱과 AI API 막기

제품 맥락: [PRODUCT.md](../../../PRODUCT.md) — 개인용 앱이라 만든 사람 한 명만 쓴다. 배포하면 주소를 아는 누구나 앱을 열 수 있어서, 로그인한 사람만 대화 화면과 AI 호출을 쓰게 막는다.

연결된 결정 계약:
- [deployment](../../decisions/deployment.md) — 배포된 앱은 Supabase 계정 로그인으로 막고, 로그인하지 않으면 AI를 부르는 서버 기능을 쓸 수 없다. 로그인 방식과 가입 제한은 이 작업에서 확정했고 계약에 반영했다.
- [ui-composition](../../decisions/ui-composition.md) — 로그인 화면은 shadcn 공식 component로 구성한다.

선행 스펙: [voice-conversation-loop](../voice-conversation-loop/spec.md)의 대화 화면과 `/api/chat`, `/api/feedback`을 보호 대상으로 쓴다.

## 사용자에게 보이는 결과

1. 로그인하지 않은 채 앱 주소를 열면 로그인 화면(`/login`)이 뜬다. 대화 화면은 보이지 않는다.
2. 이메일과 비밀번호를 넣고 로그인하면 대화 화면으로 간다. 처음 열려던 주소가 있으면 그곳으로 간다.
3. 새로고침하거나 브라우저를 다시 열어도 로그인이 유지된다.
4. 대화 화면 위쪽에 로그아웃 버튼이 있다. 누르면 로그인 화면으로 돌아가고, 다시 로그인하기 전에는 앱도 AI 호출도 쓸 수 없다.
5. 이메일이나 비밀번호가 틀리면 로그인되지 않고 안내가 보인다.
6. 회원가입 화면과 비밀번호 재설정 화면은 없다. 새 가입은 서비스 설정에서 막혀 있고, 내 계정은 Supabase 대시보드에서 미리 만들어 둔다.

## 승인된 범위

- 이메일·비밀번호 로그인, 로그아웃, 로그인 유지(쿠키 기반 세션)
- 로그인하지 않은 요청을 막는 곳: 모든 화면 경로(`/login` 제외)와 `/api/chat`, `/api/feedback`. 화면은 로그인 화면으로 보내고, API는 401로 거절한다.
- Supabase 환경 값이 없을 때의 동작(아래 제약 참고)

## 수용 기준

로컬 개발 서버(Supabase 환경 값 설정)와 단위 테스트로 확인한다. 로그인 성공 경로는 실제 Supabase 프로젝트와 사용자가 직접 입력하는 비밀번호가 필요해서 사용자가 확인한다.

- AC1. 로그인하지 않고 `/`를 열면 `/login`으로 이동하고 대화 화면은 나타나지 않는다. 원래 경로는 `next`로 기억되어 로그인 뒤 그곳으로 간다.
- AC2. 로그인하지 않고 `/api/chat`, `/api/feedback`을 부르면 401을 받고 OpenAI는 호출되지 않는다. 화면을 거치지 않고 API를 직접 불러도 막힌다.
- AC3. 올바른 이메일·비밀번호로 로그인하면 대화 화면으로 가고 새로고침해도 유지된다. 틀리면 실패 안내가 보이고 로그인되지 않는다. (사용자 확인)
- AC4. 로그인 상태의 대화 화면에 로그아웃 버튼이 있고, 누르면 새로고침 없이 로그인 화면으로 가며 이후 `/`와 두 API가 다시 막힌다.
- AC5. 로그인 화면에 회원가입, 비밀번호 재설정 링크가 없다. 가입 요청(`/auth/v1/signup`)은 서비스에서 거절된다. (사용자가 설정한 뒤 확인)
- AC6. 로그인한 사용자가 `/login`을 열면 대화 화면(`/`)으로 이동한다.
- AC7. 로그인 뒤 돌아갈 주소(`next`)는 같은 사이트의 경로만 받는다. 다른 사이트나 `//evil.com` 같은 주소는 무시하고 `/`로 간다.
- AC8. 운영(production) 환경에서 Supabase 환경 값이 없으면 모든 요청이 막힌다(열린 채로 배포되지 않는다). 개발 환경에서 값이 없으면 로그인 없이 쓸 수 있다.
- AC9. 브라우저로 내려가는 코드와 응답에는 공개용(publishable) 키만 있고 비밀(service_role) 키는 쓰지도 나타나지도 않는다.

## 확정된 제약과 이유

- **가입 닫고 내 계정만**: 가입이 열려 있으면 낯선 사람이 가입해서 내 OpenAI 비용을 쓸 수 있다. 사용자 확정.
- **로그인 방식은 이메일·비밀번호 하나**: 사용자 확정. 이메일 확인 메일은 쓰지 않는다(내 계정을 대시보드에서 확인 처리해 만든다).
- **범위는 로그인·로그아웃과 보호까지**: 프로필 테이블과 `/settings`는 만들지 않는다. 개인용 앱에는 쓸모가 거의 없다. 사용자 확정. 그래서 DB 스키마 변경이 없고 Supabase CLI도 쓰지 않는다.
- **Supabase 환경 값이 없을 때**: 개발 환경은 로그인 없이 동작해 로컬 개발을 막지 않고(`deployment` 계약의 "localhost에서만 쓰는 동안은 로그인을 요구하지 않는다"), 운영 환경은 모두 막는다. 설정 실수로 열린 채 배포되는 일을 막기 위해서다.
- **본인 확인은 서버가 검증한 정보로**: 화면과 API 모두 서버에서 검증한 로그인 정보(`getClaims`)로 판단하고, 브라우저가 보낸 사용자 정보를 믿지 않는다. 보호는 요청 앞단(proxy)과 API 핸들러 두 곳에서 한다.
- **UI 출발점**: Supabase UI Library의 공식 Password-based Auth 블록을 설치된 Next.js 16 규칙(`middleware.ts`가 아니라 `proxy.ts`)과 이 프로젝트의 shadcn 구성에 맞춰 쓴다.

## 가정 (바꿀 수 있음)

- 세션 유지 기간과 로그인 시도 제한은 Supabase 기본값을 쓴다.
- 로그인 실패 안내는 원인별로 나눈다. 틀린 이메일·비밀번호는 어느 쪽이 틀렸는지 알려 주지 않는 한 문장(이메일 또는 비밀번호가 올바르지 않음)으로, 이메일 확인이 안 된 계정은 확인 처리가 필요하다는 안내로, 연결 오류 같은 나머지는 잠시 후 다시 시도하라는 안내로 보여 준다.
- 로그인 화면의 문구는 한국어다.

## 범위 밖과 이유

- 회원가입 화면, 이메일 확인, 비밀번호 재설정, Magic Link, Google 등 다른 로그인 방식 — 가입을 닫고 한 명만 쓴다.
- profiles 테이블, `/settings`, 사용자별 데이터 저장 — 이번에 저장할 데이터가 없다. 대화 기록 저장 때 다룬다.
- 로그인 시도 제한 강화, 이상 접속 탐지 같은 보안 하드닝 — 개인용 앱 범위를 넘는다.
- 로그인 사용자 구분(여러 명) — 한 명만 쓴다.

## 남은 위험

- 브라우저가 로그인된 채 분실되면 그 기기로 앱을 쓸 수 있다. 로그아웃하거나 Supabase에서 비밀번호를 바꾸면 막힌다고 받아들인다.
- 로그인 보호는 요청 앞단과 API 핸들러가 함께 하지만, 앞으로 추가할 API 경로가 있으면 같은 확인을 붙여야 한다.
- 이 PC에서는 회사 네트워크가 막을 수 있어, 실제 Supabase 프로젝트로 로그인하는 확인은 사용자가 직접 한다.

## Setup before implementation

- Supabase 프로젝트의 Project URL과 공개용(publishable) 키를 로컬 `.env.local`과 Vercel 환경 변수에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`로 넣는다(비밀 키와 service_role 키는 넣지 않는다). 완료 조건: 두 값이 설정된 개발 서버에서 로그인하지 않고 `/`를 열면 `/login`으로 이동한다.
- Supabase 대시보드(Authentication)에서 이메일 확인(Confirm email)을 끄고(사용자 확정, 설정 위치는 Auth Providers 페이지의 Email), 새 사용자 가입을 끄고, 내 계정(이메일·비밀번호)을 직접 만든다. 이미 확인 안 된 상태로 만든 계정이 있으면 사용자 목록에서 확인 처리한다. 완료 조건: 프로젝트의 `/auth/v1/signup`을 앱 밖에서 직접 호출하면 가입이 거절되고(`signup_disabled`), 내 계정으로 로그인이 성공한다.
